# Asset Catalog — Projects & Structures

This is the operational content/model backlog for persistent project goals and reusable composed structures/configurations. See [`README.md`](README.md) for semantic tokens, `Spec`, status and priority.

A project row normally spans two distinct concerns:

```text
ProjectDefinition
  eligibility / contribution patterns / completion

world truth
  ordinary entities + properties + relations + assembly bindings + place state
```

The project system never owns duplicate roof integrity, container contents, component attachment, protection, buoyancy or similar physical truth. The `World-readable milestones` column describes **presentation/progress projections from grounded world facts**, not a second physical state machine.

## Normalization notes

- Component lists are intentionally expressed as **semantic roles with compatible family examples**. They are not recipes.
- A physical structure may exist before, after or without an active `ProjectInstance`; project cognition and world truth remain independent.
- `complete`, `damaged`, `repaired`, `functional`, `leaky`, `protected`, `stable` and similar presentation words must be grounded in world facts/derived projections rather than copied into parallel project state.
- Material stacks and debris piles are arrangements of ordinary entities unless a future requirement proves independent identity/lifecycle.

---

## Project acceptance rule

A project/structure is not production `APPROVED` until:

- required role families or interchangeable predicates are clear;
- partial stages read intentionally from gameplay camera;
- physical completion/damage/repair is reconstructable from ordinary world truth;
- required interaction regions/adapters exist without defining domain identity;
- environmental protection/hazard behavior composes through the generic domain rules;
- component substitution does not rely on exact object-pair recipes;
- `Spec` and production `Status` accurately reflect the row.
