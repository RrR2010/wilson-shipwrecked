# Reference 12 — Transport, Raft & Dock

## Purpose

Define the visual grammar for simple transport and shoreline access projects while preserving modular construction, readable buoyancy and visible repairs.

Approved visual companion:

- `visual/REFERENCE_12_TRANSPORT_RAFT_DOCK.png`

---

# Core principle

Transport projects should look like **assembled solutions to a physical problem**, not miniature realistic vehicles.

Their function should be legible from broad massing:

- raft floats;
- dock reaches water;
- bridge spans a gap;
- sled moves bulk cargo;
- mooring secures floating objects.

---

# Raft grammar

A basic raft should read as:

```text
buoyant longitudinal members
+ visible lashings
+ broad usable top surface
```

Optional upgrades may add:

- deck planks;
- cargo tie-downs;
- salvaged float elements;
- simple raised edge/support;
- attachment point for paddle/pole.

Avoid dense nautical realism.

---

# Raft evolution

Preferred visual progression:

```text
loose materials
→ tied bundle
→ basic raft
→ improved raft
→ cargo-capable raft
```

Each stage should visibly increase structural coherence or useful carrying area.

---

# Dock grammar

A dock should be composed from:

- thick support posts;
- broad deck planks;
- visible bindings/joins;
- optional mooring post;
- optional extension segment.

The shoreline connection must remain visually clear.

---

# Bridge / crossing grammar

Crossings may use:

- stepping logs;
- plank bridge;
- simple rope-supported crossing;
- low raised crossing.

Favor clear spans and thick readable supports.

Do not create intricate suspension systems unless gameplay requires them.

---

# Cargo movement

Early transport should remain primitive and physically obvious:

- cargo sled;
- dragged bundle;
- roller/log aid;
- carrying pole;
- simple tied cargo bundle.

The visual language should emphasize mass and friction rather than vehicle engineering.

---

# Damage and repair

Useful states:

```text
intact
loose lashing
missing member
partially damaged
patched
reinforced
```

Repairs should remain visible as:

- new lashings;
- replacement logs/planks;
- added braces;
- mismatched salvage float;
- reinforced mooring post.

Do not reset repaired transport to pristine appearance.

---

# Anchors and sockets

Artistically relevant points should correspond to visible structure, such as:

- mooring point;
- lashing point;
- deck/plank slot;
- float/support point;
- cargo tie-down;
- extension anchor.

These should feel physically plausible when shown in diagnostic previews.

---

# Material policy

Default:

- wood;
- rope/fiber;
- limited salvage metal/float material;
- flat shared colors;
- no unique texture maps;
- wetness through shared material state.

---

# Silhouette rules

The canonical gameplay camera should clearly separate:

- the broad raft/deck plane;
- support posts;
- water edge;
- cargo where present;
- path onto/off the structure.

Avoid too many thin posts, rails or ropes that collapse into visual noise.

---

# Acceptance criteria

A transport project passes when:

- its physical purpose is immediately readable;
- construction looks modular and improvised;
- buoyancy/support logic is visually plausible;
- evolution stages show meaningful capability change;
- damage/repair adds history;
- the structure remains simple at gameplay distance;
- nautical detail does not overwhelm the project visual language.
